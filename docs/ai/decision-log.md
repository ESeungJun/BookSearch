# 의사결정·AI 활용 기록

작성자(사람)가 내린 판단과 AI 를 어디에 썼는지를 남긴다. README 「AI 활용」 절은 이 문서에서만 옮겨 쓴다.

**기록 규칙**
- 작성자가 실제로 한 판단만 적는다. 확인받지 않은 AI 추천은 1절 「세부 규칙」 표에 `추천안 기본 채택`으로 적고 작성자 검토를 받는다.
- AI 제안과 다르게 정한 것은 `AI 제안과 다름`으로 표시한다. README 「직접 판단해 바꾼 부분」은 이 표시에서만 옮긴다.
- 주제별로 **지금 유효한 상태**를 적는다. 같은 주제를 다시 정하면 새 행을 만들지 않고 그 행을 고친다. 사소한 결정은 묶어 짧게 쓴다.
- 결정에 번호를 매기지 않는다. 코드·커밋·다른 문서는 이 문서를 번호로 참조하지 않는다(정리할 때 참조가 깨지지 않게).

## 1. 결정 (주제별, 현재 상태)

### 진행·기록

| 주제 | 지금 규칙 | 작성자 판단 (AI 제안 → 결정) | 구분 |
|---|---|---|---|
| v1 폐기 | v1 프로젝트·저장소를 폐기하고 새로 만든다. v1 은 비공개 보관 | 작성자가 구조·코드를 직접 검토하고 9가지 문제로 폐기 결정 — 파일·모듈 과다, 읽기 어려운 코드, data 가 Context 로 연결 상태를 판단, 과도한 예외 처리, app 의 navigation 패키지 한곳에 몰림, 선언 순서 제각각, 새로고침을 trigger Flow 로 처리, 쓸모없는 Room 스키마 이력, data 패키지 과다. 보관 방식은 AI 추천(이름 변경 + 비공개) 채택 | 사용자 지시 |
| 진행 방식 | 단계마다 파일 목록 승인 → 구현 → diff 검토 → 병합. plan-haul 이 기획서, dev-haul 이 3단계부터 단계 위임으로 구현하고 메인 세션이 검토. dev-haul 자체도 v1 실패 사례와 v2 규칙에 맞게 고침 | AI 는 메인 세션 직접 구현만 제안 → 작성자가 "만든 에이전트의 활용도도 보여 주고 싶다"며 에이전트 사용과 개정을 지시 | AI 제안과 다름 |
| 커밋 | 머리말 `[feat]`·`[fix]`·`[refac]`·`[docs]`·`[merge]`·`[chore]`. 코드와 그 결정 기록을 한 커밋으로. 이미 올린 8개 커밋은 한 번만 예외로 이력 재작성(force push) | 작성자 지시. 재작성 여부는 AI 가 올린 두 안 중 작성자가 선택 | 사용자 지시 |
| 이어받기 문서·에이전트 | 쓸모를 다한 문서(v1 기록·AI 단독 결정 목록)는 지우고, `ARCHITECTURE.md`(앱 전체) + 레이어별 `README.md`(app·core·presentation·domain·data)로 구조를 설명한다. 저장소에 온보딩 에이전트(문서·코드 근거로 사실만 답함, 읽기 전용)와 기능 개발 에이전트(`docs/guide/기능-추가.md` 를 따름)를 둔다. 구조를 바꾸면 같은 커밋에서 해당 구조 문서를 고친다. 저장소에서 `claude` 를 실행하면 온보딩 에이전트가 메인 세션으로 시작하고(`.claude/settings.json` 의 `agent`), 이 기기에서 처음 연 세션이면 먼저 인사하며 구조를 설명한다(세션 시작 훅이 표시 파일로 처음인지 알림). 기능 개발 요청은 온보딩이 `feature-dev` 에 넘긴다 | 작성자가 "구조 md + 레이어별 설명 + 문답용 온보딩 에이전트 + 개발용 에이전트"를 제안 → AI 가 "왜"를 담은 결정 기록·기획서는 지우지 말 것, 모듈마다가 아니라 레이어마다 문서를 둘 것, 개발 에이전트는 개인 에이전트를 옮기지 말고 가이드 문서 + 얇은 에이전트로 할 것을 제안 → 작성자가 채택. 이후 작성자가 "실행하자마자 온보딩이 먼저 말을 걸게" 지시 → AI 가 공식 기능(에이전트 `initialPrompt` + 기본 에이전트 설정)과 제약(모든 세션에 적용, 읽기 전용)을 알리고 세 안을 제시 → 작성자가 "기본 에이전트 + 처음만 설명"을 고름 | 사용자 지시 |

### 구조

| 주제 | 지금 규칙 | 작성자 판단 (AI 제안 → 결정) | 구분 |
|---|---|---|---|
| 모듈 | 레이어 × 기능. 공통은 `:core:designsystem`·`:core:network`·`:core:navigation`·`:domain:base`·`:data:base`(결과 변환·Room DB), domain 은 주제별(`search`·`favorite`·`book`), data 는 출처별(`api/<API 경로>`·`local/<저장 대상>`), presentation 은 `feature/<기능>` 화면별. Hilt 모듈은 바인딩을 구현한 모듈의 `di/` 패키지에 두고 별도 di 모듈은 없다. 패키지 이름 = 모듈 경로(`data.api.searchbook.repo`), `:app` 만 applicationId | AI 는 처음 기능 모듈(`:core:*`+`:feature:*`)을 냈다 → 작성자가 레이어 우선 + 레이어당 모듈 하나로 시작 → 이후 작성자가 domain·data·di 를 기능별로, 공통 `book` 모듈은 `base`(타입)·`database`(DB)·`detail`(상세)로, 디자인 시스템은 `:core` 로, 네트워크 주입은 `:di:network` 로 나눔. DB 는 data 모듈끼리 참조가 꼬이지 않게 `:core:database` 로, 의존은 `api` 없이 `implementation` 만, 레이어 공통 의존은 레이어별 컨벤션 플러그인으로 묶음. 리뷰에서 모듈 수가 코드 양에 비해 많다는 점을 짚음 → 작성자가 기능별 di 모듈의 장점(바뀐 기능만 다시 빌드, 기능별 연결이 보임)을 유지하는 쪽으로, 바인딩을 각 data·core 모듈의 di 패키지로 옮기고 di 모듈을 없앰. 이후 작성자가 data 는 API 경로 단위로 나누되 "domain 은 데이터가 api 에서 오는지 local 에서 오는지 관심이 없다"며 domain 은 출처로 나누지 않게 정함. 여러 출처를 조합하는 biz UseCase 층은 지금 조합할 행동이 없어 두지 않음 | AI 제안과 다름 |
| 화면 이동 | 공용 `:presentation:router` 에 화면마다 `XxxRouter`(넘길 값 `PageData` + `open`). 다른 기능 화면으로 갈 때는 Router 를 주입받아 `open` 만 부르고, 구현 `XxxRouterImpl` 은 그 화면의 main 모듈이 `:core:navigation` 의 `INavigator` 로 만들어 Hilt 로 바인딩한다. PageData → 화면 연결도 각 main 이 Hilt 로 내놓고 `:app` 이 모아 그린다. Navigation 3 유지 | 처음에는 화면이 콜백만 내놓고 `:app` 이 모든 이동을 연결했다 → 작성자가 기능 모듈 전체를 알면 의존 그래프가 무너진다며 라우터 분리를 지시 → 기능별 route 모듈(경로만)을 거쳐, 작성자가 원한 형태(공용 router 모듈 + 화면별 Router 추상 클래스와 main 의 구현)로 바꿈. 생성자 주입 값은 모두 `private val` 로 통일 | AI 제안과 다름 |
| data 내부 | `repo`(원격·로컬 중 어디서 가져올지, 원본 → DTO 변환) · `source/remote`(API) · `source/local`(DB·캐시) · `service`(I~Service) · `data`(~Api). Room DB·DAO·Entity 는 `:data:base` 한곳(Room 제약, 기능 data 모듈끼리 참조하지 않게 공통 기반에). 서버 호출의 결과 변환은 `:data:base` 의 `safeApiCall {}` 하나로 공통화. 데이터 소스는 자기 원본 타입(`~Api`·`~Entity`)만 주고받는다 | AI 는 데이터 소스 없이 저장소가 API·DAO 직접 호출 → 작성자가 클린 아키텍처 기준으로 데이터 소스 분리와 패키지 구성을 지시. Room 위치는 AI 가 올린 선택지 중 작성자가 별도 루트를 택함 → 이후 `:core:database` 로 옮겼다가, 작성자가 "core 는 레이어와 무관한 기반이고 DB 는 앱 데이터를 담는 data 의 일"이라며 `:data:base` 안으로 합침(AI 는 `:data:base` 합침과 별도 `:data:db` 를 비교해 합침을 추천). 호출마다 반복되던 try-catch 를 공통 코드로 빼라고 작성자가 지시. 처음에는 데이터 소스가 DTO 로 바꿔 주었으나, 작성자가 "source 는 원본을 그대로 넘기고 필요하면 repo 가 매핑"하도록 정함 | AI 제안과 다름 |
| domain 의 역할 | UseCase 는 **사용자 행동 정의서** — 행동 하나에 `invoke` 하나, 저장소 함수 하나를 부른다. 판단 로직(필터·정렬·분기)은 두지 않고 데이터 판단은 `:data:<기능>`, 입력·표시·정렬은 `:presentation:<기능>`. 패키지는 `data`·`repo`·`usecase`. 결과는 `DomainResult`(Success·Fail(code)·Error(cause))로 상황만 전하고 원인은 data 가 채우고 화면이 판단한다. 결과의 공통 처리는 레이어마다 따로 둔다 — data 는 `safeApiCall {}`, 모든 저장소 함수가 `DomainResult` 를 돌려주고(data 의 `safeApiCall {}`·`safeDbCall {}`·`safeDbFlow()` 가 만듦), UseCase 는 그 결과를 그대로 돌려준다 | AI 는 단순 위임 UseCase 를 만들지 말자, 필터는 UseCase 안에, 결과는 `Result`+예외(원인 enum) → 작성자가 행동 정의서 원칙, 로직 분리, 원인 없는 결과 타입, 정렬은 화면을 지시. 결과를 받는 쪽은 `if`/`as?` 로 성공만 고르지 말고 `when` 으로 세 상황을 모두 적으라고 작성자가 지시 | AI 제안과 다름 |
| UseCase 구성 | 검색·정렬 변경·새로고침·다음 페이지 모두 `SearchBooksUseCase(query, sort, page)` 하나. 즐겨찾기는 `ToggleFavoriteUseCase(book, isFavorite)` 하나. Custom Tab(전체 소개 보기)은 UseCase 없이 화면 동작 | 다음 페이지는 작성자가 한때 `LoadMoreBooksUseCase` 로 나눴다가, 같은 저장소 함수를 페이지만 바꿔 부르므로 나눌 의미가 없다며 다시 하나로 합침. 토글 하나 유지도 AI 의 "둘로 나누기"와 다름. Custom Tab 은 AI 추천 채택. 앱 시작 시 마지막 검색 복원은 plan-haul 제안으로 넣었다가, 작성자가 "검색어 기반으로 찾을 수 있어야 한다"며 빼고 오프라인 검색을 넓히는 쪽으로 바꿈 | AI 제안과 다름(1) · 사용자 확정(3) |
| DI 범위 | 저장소·데이터 소스는 `ViewModelComponent` + `@ViewModelScoped`. 싱글톤은 앱에 하나여야 동작하는 Room DB·OkHttp·Retrofit 만 | AI 는 저장소 `@Singleton` → 작성자가 ViewModel 범위로 한정하고, 데이터 소스에도 범위를 붙이자고 제안. DB·네트워크 싱글톤 유지는 AI 근거(Room 변경 감지·연결 풀)를 작성자가 받아들임 | AI 제안과 다름 |
| 이름 | 서버 응답 `~Api`, Retrofit `I~Service`, 테이블 `~Entity`, domain 데이터 `~DTO`(enum 제외), 화면 `~UiState`·`~ViewData`, 화면 조각 `<기능>~View`(internal), 본문 `<기능>Content`(internal), 인터페이스 `I~`·구현체 `~Impl`, 추상 `Abs~`, 베이스 `Base~` | AI 는 `~Response`·접미사 없는 모델·접두사 없는 인터페이스 → 작성자가 규칙을 정함. 겹치는 곳(Retrofit 이름 등)은 AI 추천 채택. 이후 작성자가 화면 조각을 기능 이름으로 시작해 `View` 로 끝나게 하고(구분), 모듈 밖에서 안 쓰는 `~Content` 를 internal 로 정함 | AI 제안과 다름 |

### 데이터·동작

| 주제 | 지금 규칙 | 작성자 판단 (AI 제안 → 결정) | 구분 |
|---|---|---|---|
| 응답 null 처리 | `~Api` 필드는 전부 nullable·기본값 없음. 서버가 안 보낸 값은 null 그대로 화면까지 가고 화면이 판단한다. 목록·총 개수가 없으면 에러 | AI 는 기본값(`""`·0·-1)을 넣고 빈 값을 null 로 바꿈 → 작성자가 "빈 값으로 판단하면 예외가 많다"며 서버 값을 그대로 믿기로 함 | AI 제안과 다름 |
| 매칭 키·검색 캐시 | v1 규칙 유지: 키 ISBN13 → ISBN10 → 제목+저자+출판사, 캐시는 (검색어·정렬) 20조합 LRU × 5페이지·만료 없음, 네트워크 먼저 3초 넘거나 실패하면 캐시 | 작성자가 v1 결정을 그대로 가져가기로 함. 테이블은 책·즐겨찾기·검색 캐시 3개(AI 추천 채택) | 사용자 확정 |
| 실패 시 동작 | 자동 재시도 없이 "다시 시도" 버튼. 네트워크가 실패하면 같은 검색의 저장 결과 → 없으면 기기에 저장된 모든 책에서 검색어로 찾은 결과 → 둘 다 없으면 오류 화면. 오류 문구는 원인(연결·키 오류·서버·DB)과 관계없이 "네트워크 또는 서버가 원활하지 않아요. 잠시 후 다시 시도해 주세요" 하나 | AI 는 통신 계층 GET 2회 자동 재시도 → 작성자가 버튼을 택함(plan-haul 기획서 제안과 같음). 키 오류 때 캐시로 덮여 원인이 안 보이는 점을 AI 가 리뷰에서 짚었고, 작성자가 "캐시는 보여 주되 토스트만"으로 정했다가, 이후 키 오류를 따로 알릴 필요가 없다며 토스트와 원인별 문구를 없애고 한 문구로 줄임. 오프라인에서 새 검색어는 바로 오류가 되던 점을 작성자가 짚어, 저장된 모든 책에서 찾는 단계를 더함. 리뷰에서 AI 가 3초 고정의 한계(느린 연결에서 네트워크 결과를 못 받음)를 짚고 "저장 결과를 먼저 보이고 응답을 계속 기다리기"를 제안 → 작성자가 응답이 와서 목록이 통째로 바뀌는 것이 더 나쁘다며 하지 않기로 정함 | AI 제안과 다름 |
| 다음 페이지 요청 시점 | 목록 끝에서 10칸(반 페이지) 남았을 때 부른다 | AI 는 5칸으로 정했다 → 작성자가 실행해 보고 빠르게 내리면 응답 전에 끝에 닿아 스크롤이 끊기고 프로그레스가 안 보인다고 짚어 앞당김 | AI 제안과 다름 |
