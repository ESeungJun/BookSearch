# 의사결정·AI 활용 기록

작성자(사람)가 내린 판단과 AI 를 어디에 썼는지를 남긴다. README 「AI 활용」 절은 이 문서에서만 옮겨 쓴다.

**기록 규칙**
- 작성자가 실제로 한 판단만 적는다. 확인받지 않은 AI 추천은 `추천안 기본 채택`으로 적고 `REVIEW.md` 에 모은다.
- AI 제안과 다르게 정한 것은 `AI 제안과 다름`으로 표시한다. README 「직접 판단해 바꾼 부분」은 이 표시에서만 옮긴다.
- 주제별로 **지금 유효한 상태**를 적는다. 같은 주제를 다시 정하면 새 행을 만들지 않고 그 행을 고친다. 사소한 결정은 묶어 짧게 쓴다.
- 결정에 번호를 매기지 않는다. 코드·커밋·다른 문서는 이 문서를 번호로 참조하지 않는다(정리할 때 참조가 깨지지 않게). v1 기록은 `v1-decision-log.md` 에 원문 그대로 있다.

### 구조

| 주제 | 지금 규칙 | 작성자 판단 (AI 제안 → 결정) | 구분 |
|---|---|---|---|
| 모듈 | 레이어 × 기능. 공통은 `:core:designsystem`·`:core:database`·`:core:network`·`:domain:base`·`:data:base`, 나머지는 `search`·`favorite`·`detail` 기능별. Hilt 모듈은 바인딩을 구현한 모듈의 `di/` 패키지에 두고 별도 di 모듈은 없다. 패키지 이름 = 모듈 경로(`data.search.repo`), `:app` 만 applicationId | AI 는 처음 기능 모듈(`:core:*`+`:feature:*`)을 냈다 → 작성자가 레이어 우선 + 레이어당 모듈 하나로 시작 → 이후 작성자가 domain·data·di 를 기능별로, 공통 `book` 모듈은 `base`(타입)·`database`(DB)·`detail`(상세)로, 디자인 시스템은 `:core` 로, 네트워크 주입은 `:di:network` 로 나눔. DB 는 data 모듈끼리 참조가 꼬이지 않게 `:core:database` 로, 의존은 `api` 없이 `implementation` 만, 레이어 공통 의존은 레이어별 컨벤션 플러그인으로 묶음. 리뷰에서 모듈 수가 코드 양에 비해 많다는 점을 짚음 → 작성자가 기능별 di 모듈의 장점(바뀐 기능만 다시 빌드, 기능별 연결이 보임)을 유지하는 쪽으로, 바인딩을 각 data·core 모듈의 di 패키지로 옮기고 di 모듈을 없앰 | AI 제안과 다름 |
| 화면 이동 | 공용 `:presentation:router` 에 화면마다 `XxxRouter`(넘길 값 `PageData` + `open`). 다른 기능 화면으로 갈 때는 Router 를 주입받아 `open` 만 부르고, 구현 `XxxRouterImpl` 은 그 화면의 main 모듈이 `:core:navigation` 의 `INavigator` 로 만들어 Hilt 로 바인딩한다. PageData → 화면 연결도 각 main 이 Hilt 로 내놓고 `:app` 이 모아 그린다. Navigation 3 유지 | 처음에는 화면이 콜백만 내놓고 `:app` 이 모든 이동을 연결했다 → 작성자가 기능 모듈 전체를 알면 의존 그래프가 무너진다며 라우터 분리를 지시 → 기능별 route 모듈(경로만)을 거쳐, 작성자가 원한 형태(공용 router 모듈 + 화면별 Router 추상 클래스와 main 의 구현)로 바꿈. 생성자 주입 값은 모두 `private val` 로 통일 | AI 제안과 다름 |
| data 내부 | `repo`(원격·로컬 중 어디서 가져올지) · `source/remote`(API) · `source/local`(DB·캐시) · `service`(I~Service) · `data`(~Api). Room DB·DAO·Entity 는 `:core:database` 한곳(Room 제약, 기능 data 모듈끼리 참조하지 않게 core 로). 서버 호출의 결과 변환은 `:data:base` 의 `safeApiCall {}` 하나로 공통화 | AI 는 데이터 소스 없이 저장소가 API·DAO 직접 호출 → 작성자가 클린 아키텍처 기준으로 데이터 소스 분리와 패키지 구성을 지시. Room 위치는 AI 가 올린 선택지 중 작성자가 별도 루트를 택함. 호출마다 반복되던 try-catch 를 공통 코드로 빼라고 작성자가 지시 | AI 제안과 다름 |
| domain 의 역할 | UseCase 는 **사용자 행동 정의서** — 행동 하나에 `invoke` 하나, 저장소 함수 하나를 부른다. 판단 로직(필터·정렬·분기)은 두지 않고 데이터 판단은 `:data:<기능>`, 입력·표시·정렬은 `:presentation:<기능>`. 패키지는 `data`·`repo`·`usecase`. 결과는 `DomainResult`(Success·Fail(code)·Error(cause))로 상황만 전하고 원인은 data 가 채우고 화면이 판단한다. 결과의 공통 처리는 레이어마다 따로 둔다 — data 는 `safeApiCall {}`, 모든 저장소 함수가 `DomainResult` 를 돌려주고(data 의 `safeApiCall {}`·`safeDbCall {}`·`safeDbFlow()` 가 만듦), UseCase 는 그 결과를 그대로 돌려준다 | AI 는 단순 위임 UseCase 를 만들지 말자, 필터는 UseCase 안에, 결과는 `Result`+예외(원인 enum) → 작성자가 행동 정의서 원칙, 로직 분리, 원인 없는 결과 타입, 정렬은 화면을 지시 | AI 제안과 다름 |
| UseCase 구성 | 검색·정렬 변경·새로고침은 `SearchBooksUseCase`(1페이지), 다음 페이지는 `LoadMoreBooksUseCase`. 즐겨찾기는 `ToggleFavoriteUseCase(book, isFavorite)` 하나. 앱 시작 시 마지막 검색 복원 `GetLastSearchUseCase`. Custom Tab(전체 소개 보기)은 UseCase 없이 화면 동작 | 다음 페이지 분리는 AI 의 "하나로 유지"와 다르게 작성자가 정함. 토글 하나 유지도 AI 의 "둘로 나누기"와 다름. 마지막 검색 복원·Custom Tab 은 AI 추천 채택 | AI 제안과 다름(2) · 사용자 확정(2) |
| DI 범위 | 저장소·데이터 소스는 `ViewModelComponent` + `@ViewModelScoped`. 싱글톤은 앱에 하나여야 동작하는 Room DB·OkHttp·Retrofit 만 | AI 는 저장소 `@Singleton` → 작성자가 ViewModel 범위로 한정하고, 데이터 소스에도 범위를 붙이자고 제안. DB·네트워크 싱글톤 유지는 AI 근거(Room 변경 감지·연결 풀)를 작성자가 받아들임 | AI 제안과 다름 |
| 이름 | 서버 응답 `~Api`, Retrofit `I~Service`, 테이블 `~Entity`, domain 데이터 `~DTO`(enum 제외), 화면 `~UiState`·`~ViewData`, 인터페이스 `I~`·구현체 `~Impl`, 추상 `Abs~`, 베이스 `Base~` | AI 는 `~Response`·접미사 없는 모델·접두사 없는 인터페이스 → 작성자가 규칙을 정함. 겹치는 곳(Retrofit 이름 등)은 AI 추천 채택 | AI 제안과 다름 |

### 데이터·동작

| 주제 | 지금 규칙 | 작성자 판단 (AI 제안 → 결정) | 구분 |
|---|---|---|---|
| 응답 null 처리 | `~Api` 필드는 전부 nullable·기본값 없음. 서버가 안 보낸 값은 null 그대로 화면까지 가고 화면이 판단한다. 목록·총 개수가 없으면 에러 | AI 는 기본값(`""`·0·-1)을 넣고 빈 값을 null 로 바꿈 → 작성자가 "빈 값으로 판단하면 예외가 많다"며 서버 값을 그대로 믿기로 함 | AI 제안과 다름 |
| 매칭 키·검색 캐시 | v1 규칙 유지: 키 ISBN13 → ISBN10 → 제목+저자+출판사, 캐시는 (검색어·정렬) 20조합 LRU × 5페이지·만료 없음, 네트워크 먼저 3초 넘거나 실패하면 캐시 | 작성자가 v1 결정을 그대로 가져가기로 함. 테이블은 책·즐겨찾기·검색 캐시 3개(AI 추천 채택) | 사용자 확정 |
| 실패 시 동작 | 자동 재시도 없이 "다시 시도" 버튼. 저장해 둔 결과가 있으면 실패해도 그것을 보여 주고, 원래 실패를 함께 넘겨 키 오류(401·403)는 토스트로만 알린다 | AI 는 통신 계층 GET 2회 자동 재시도 → 작성자가 버튼을 택함(plan-haul 기획서 제안과 같음). 키 오류 때 캐시로 덮여 원인이 안 보이는 점을 AI 가 리뷰에서 짚었고, 작성자가 "캐시는 보여 주되 토스트만"으로 정함 | AI 제안과 다름 |
| 즐겨찾기 금액 구간 | 전체 / 1만 원 미만 / 1~2만 / 2~3만 / 3만 이상 | plan-haul 추천 채택 | 사용자 확정 |
| v1 에서 이어받은 화면 결정 | 상세는 식별자로 로컬 조회, 중간 폭도 2칸, 디바운스 실시간 검색, 맨 위로·페이징 프로그레스, 첫 진입 스켈레톤·새로고침 프로그레스, 좌우 슬라이드 전환, 정렬 바꾸면 맨 위, 총 개수·카드 보조 줄, 소개 요약 + 전체 소개 보기, 스크롤 시 개수·정렬 줄만 고정 | 경위는 `v1-decision-log.md`. 최근 검색어 기능은 v1 에서 삭제 | 대부분 AI 제안과 다름 |
